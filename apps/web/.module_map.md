# Web Module Map

## Scope
- Implements the frontend application shell, unauthenticated public transparency site, Auth/Session UI, Residents/Houses/Areas management UI, mode-aware Jimpitan operational flows, and Finance/Ledger/Approval UI: public/private route groups, dashboard shell, same-origin auth API route handlers, same-origin backend proxy for business APIs, httpOnly token cookie strategy, session refresh/logout, same-origin POST validation, navigation, tenant context provider, API client, query keys, form/table foundations, loading/error/empty states, notification UI foundation, design tokens, Next.js proxy guard, and Docker readiness.
- Remaining private settings pages are placeholders only. Private reports now expose export lifecycle controls; no PDF/Excel generation UI, Telegram UI, mock business data, payment gateway, AI analytics, or backend business logic duplication is implemented.

## Route Groups
- `src/app/(public)`: public home, finance summary, monthly reports, collection summary, announcement feed, loading skeleton, and error boundary.
- `src/app/(auth)`: login route scaffold.
- `src/app/(dashboard)`: private dashboard layout plus implemented Residents, Houses, Areas, Jimpitan, Finance/Ledger, Approval, and report export routes; settings remains placeholder.
- `src/app/api/health`: lightweight frontend process health endpoint for containers and reverse proxy checks.
- `src/app/api/auth`: same-origin login/session/refresh/logout routes that bridge browser UI to backend Auth APIs without exposing tokens to JavaScript.
- `src/app/api/backend/[...path]`: allowlisted same-origin proxy for tenant-scoped Residents/Houses/Areas/Jimpitan/Finance/Ledger/Approval/Reports backend APIs plus membership lookup for officer assignment.
- `src/proxy.ts`: private route guard that keeps dashboard routes behind a session cookie and prevents authenticated users from staying on login.

## Boundaries
1. Server components own layout composition and server cookie reads.
2. Client providers own TanStack Query, theme, toast, tenant context, and interactive shell UI.
3. `src/lib/api` owns HTTP calls and never hardcodes API URLs.
4. `src/lib/query` owns tenant-scoped query keys.
5. `src/lib/navigation` owns permission-aware route metadata and is the single source for sidebar/mobile nav.
6. `src/components/ui` contains shadcn-compatible primitives only.
7. `src/components/app-shell`, `feedback`, `forms`, and `data-table` provide generic shell foundations, not business page implementations.
8. `src/features/structure` owns Residents/Houses/Areas feature APIs, hooks, schemas, forms, pages, and tests.
9. `src/features/jimpitan` owns collection session APIs, mode contracts, hooks, schemas, workflow helpers, session pages, per-house and bulk-total mobile field input, lifecycle dialogs, and tests.
10. `src/features/finance` owns finance, ledger, approval, and private report export APIs, hooks, schemas, workflow helpers, forms, lifecycle dialogs, pages, export panel, and tests.
11. `src/features/public-reports` owns unauthenticated public report API calls, public CSV export links, Indonesian formatting, public RT/month/search sanitization, private-field safety guard, public report components, and tests.

## Component Hierarchy
1. `src/app/layout.tsx` wraps all routes with `AppProviders`.
2. `AppProviders` wires theme, TanStack Query, and toast rendering.
3. Public routes render through `PublicShell` and the `public-reports` feature components.
4. Auth routes render standalone auth forms.
5. Dashboard routes read session metadata server-side, then render `DashboardShell`.
6. `DashboardShell` validates the current session through TanStack Query before rendering protected children.
7. `DashboardShell` wraps `TenantProvider`, `DashboardSidebar`, `Topbar`, and `MobileNav`.
8. Placeholder pages use `PlaceholderPage` and `EmptyState` only until business pages are implemented.

## Auth Session Flow
1. Login form posts credentials to `/api/auth/login`.
2. The route handler calls backend `POST /auth/login`, stores access and refresh tokens in httpOnly cookies, stores non-sensitive session metadata, and returns session metadata only.
3. Dashboard proxy allows an access cookie, or a refresh cookie paired with session metadata, so expired access tokens can refresh without protected content rendering first.
4. Dashboard layout redirects when no session metadata cookie exists; `DashboardShell` then calls `/api/auth/session` to validate access and load profile/tenant context before rendering children.
5. `/api/auth/session` refreshes expired access tokens with the httpOnly refresh cookie and avoids clearing cookies on refresh failure to prevent concurrent refresh responses from erasing newer cookies.
6. Logout posts to `/api/auth/logout`, attempts backend refresh-session revocation, clears cookies, resets session query cache, and redirects to login.
7. Tenant switching is limited to tenants that have a usable permission context in the current session; other RTs remain visible but require a fresh RT-scoped login before activation.
8. Public transparency pages call backend `/reports/public/:rtCode/*` endpoints and public CSV export URLs directly without cookies, bearer tokens, or tenant headers.
9. Residents/Houses/Areas pages call `/api/backend/*`, which rejects tenant header mismatches and forwards backend requests with httpOnly bearer cookies only on the server.

## Security Review Notes
- Auth route handlers reject cross-site browser POSTs through Origin/Sec-Fetch-Site validation.
- Browser auth clients call same-origin `/api/auth/*` routes only and never receive backend access or refresh tokens.
- Public transparency pages call backend public report endpoints directly with omitted credentials, reject private-shaped payload fields before rendering, and avoid hardcoded tenant fallback.
- Server-only backend Auth adapters are guarded with the `server-only` package.
- API URL joining preserves configured base paths such as `/api/v1` and rejects absolute override URLs.
- Login redirects are restricted to dashboard-relative paths.
