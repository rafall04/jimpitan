# API Module Map

## Scope
- NestJS backend skeleton plus Auth/RBAC, Tenant/User/Membership, Residents, Houses, Areas, Jimpitan collection foundation logic, Finance/Ledger foundation logic, Expense Approval workflow logic, Notification workflow logic, Telegram Bot integration logic, and worker process foundation logic.
- Login, refresh token rotation, logout, current principal resolution, tenant membership resolution, permission checking, minimal RT CRUD, tenant-scoped user management, membership management, role/permission assignment, resident CRUD/lifecycle, house CRUD/archive, area CRUD/archive, Jimpitan collection lifecycle workflows, finance/ledger foundation workflows, expense approval workflows, notification workflows, Telegram bot workflows, reporting workflows, public transparency reads, and export engine foundation are implemented.
- No email provider delivery integration, audit browsing, or attachment workflow logic is implemented.

## Entry Points
- `src/main.ts`: API bootstrap, versioning, validation, exception filter, Swagger.
- `src/bootstrap/admin.ts`: one-shot first-admin CLI bootstrap command for production API containers.
- `src/app.module.spec.ts`: root AppModule DI regression test that compiles the real module graph and guards explicit token injection for function dependencies.
- `src/worker/main.ts`: worker bootstrap, application context lifecycle, polling loop entry, and graceful shutdown.
- `src/app.module.ts`: module wiring and correlation middleware.
- `src/health/health.controller.ts`: API liveness and PostgreSQL readiness endpoints.

## Infrastructure
- `src/config`: environment validation and typed configuration.
- `src/bootstrap`: first-admin bootstrap parser, service, module, CLI entrypoint, and tests.
- `src/runtime/logging.ts`: shared logging level resolver for API and worker processes.
- `src/worker`: background worker module, service, and tests for report export and notification/Telegram outbox processing.
- `src/prisma`: Prisma module and service boundary.
- `src/common`: decorators, guards, interceptors, filters, pipes, constants, types, utilities.
- `src/common/middleware`: request middleware such as correlation ID propagation.
- `src/common/decorators/permissions.decorator.ts`: RBAC metadata decorator.
- `src/common/decorators/public-route.decorator.ts`: public route metadata decorator.
- `src/common/decorators/current-user.decorator.ts`: current principal decorator.
- `src/common/decorators/tenant-context.decorator.ts`: resolved tenant context decorator.
- `src/common/guards`: authentication, tenant, and permission guards provided by Auth/RBAC modules.

## Auth/RBAC Flow
1. `POST /api/v1/auth/login` validates credentials, requires explicit RT selection for multi-membership users, creates a hashed refresh-token session, signs tenant-scoped JWTs, and writes auth audit with correlation ID.
2. `POST /api/v1/auth/refresh` verifies refresh JWT claims, checks the stored refresh hash, atomically rotates the hash, preserves tenant context, revokes on replay/race detection, and writes auth audit.
3. `POST /api/v1/auth/logout` verifies the presented refresh token against the stored session hash before revoking and auditing.
4. `GET /api/v1/auth/me` validates tenant-scoped access-token claims and returns the current principal only.
5. `AuthenticationGuard` resolves the principal from the database on each protected request; `TenantGuard` enforces token tenant context; `PermissionGuard` checks route metadata after membership resolution and denies unscoped super-admin checks.

## Tenant/User/Membership Flow
1. Tenant endpoints require Auth/RBAC guards; non-super-admin reads/updates are scoped to the current RT, while tenant create/delete requires `SUPER_ADMIN`.
2. User admin endpoints use `AuthenticationGuard`, `TenantGuard`, and `PermissionGuard`; list queries always use `actor.rtId`.
3. User updates first verify the target user has a membership in the current RT.
4. Membership role assignment validates role tenant ownership, blocks `SUPER_ADMIN` role grants by non-super-admin actors, and prevents granting permissions outside the actor permission set unless the actor is `SUPER_ADMIN`.
5. Role permission assignment only updates tenant-owned roles and prevents assigning permissions outside the actor permission set unless the actor is `SUPER_ADMIN`.
6. User and membership mutations write audit logs for user created, user updated, membership created, membership role changed, and membership disabled.
7. Tenant mutations return a safe tenant shape and write audit logs for tenant created, tenant updated, and tenant deleted.

## Residents/Houses/Areas Flow
1. Resident, house, and area endpoints use `AuthenticationGuard`, `TenantGuard`, and `PermissionGuard`; every repository query receives `actor.rtId`.
2. Area CRUD supports search, sorting, pagination, and archive; archive is blocked while active houses reference the area.
3. House CRUD supports area grouping, search, status filtering, sorting, pagination, and archive; archive is blocked while active residents reference the house.
4. Resident CRUD supports search by resident name/phone/house/area, filters by house/area/status, sorting, pagination, archive/reactivate lifecycle, and house moves.
5. Resident assignment validates the target house belongs to the current RT and is not archived or inactive, with repository-level transaction rechecks before writing.
6. Resident create, archive, reactivate, and house move synchronize house occupancy status and write `HOUSE_OCCUPANCY_CHANGED` audit logs when status changes.
7. Optional resident Telegram binding validates the account exists, is not revoked, and is not already bound in the same RT before writing the binding, then rechecks those conditions inside the write transaction.
8. House `OCCUPIED` status is derived from active residents; creating occupied houses or marking vacant houses occupied is rejected.

## Jimpitan Collection Flow
1. Jimpitan endpoints use `AuthenticationGuard`, `TenantGuard`, and `PermissionGuard`; repository calls are always scoped by `actor.rtId`.
2. Collection create/update validates active same-tenant officer membership and active same-tenant route area before writing.
3. Active duplicate route/date sessions are blocked by service preflight plus serializable repository rechecks for create/update.
4. Collection mode defaults to `PER_HOUSE`; `BULK_TOTAL` is total-only and `HYBRID` remains schema/API foundation.
5. Checklist generation returns route houses with primary resident defaults for `PER_HOUSE`; `BULK_TOTAL` returns no houses and uses the `bulk-total` endpoint.
6. Item batch input validates one item per house per batch, active route houses, active in-house residents, item amount/status consistency, and database uniqueness on `(collectionId, houseId)`.
7. Submitted sessions require mode-specific readiness: at least one item for `PER_HOUSE`, positive integer total for `BULK_TOTAL`; validated/rejected transitions require `SUBMITTED`, and conditional transactional updates prevent stale lifecycle writes.
8. Validation emits composite hook events; finance posting and notification outbox writes run through decoupled adapters, and Telegram command input calls the service through the same application boundary.
9. Summary and outstanding endpoints derive item progress for `PER_HOUSE`; `BULK_TOTAL` summaries use session totals and outstanding returns empty.

## Finance/Ledger Flow
1. Finance and ledger endpoints use `AuthenticationGuard`, `TenantGuard`, and `PermissionGuard`; every repository query receives `actor.rtId`.
2. Cash accounts and transaction categories support tenant-scoped list/detail/create/update/archive, and inactive or archived rows cannot be used for new finance effects.
3. Transaction creation supports income and expense drafts, strict cash amount precision, category/account validation, and tenant-scoped idempotency keys; source collections must use the dedicated posting endpoint.
4. Transaction validation moves `DRAFT` to `VALIDATED`; rejection accepts `DRAFT` or `VALIDATED`; voiding accepts `DRAFT` only; posted transactions are immutable.
5. Posting accepts `VALIDATED` transactions only and writes transaction status, ledger row, ledger sequence, balance mirror, and audit logs inside one serializable database transaction.
6. Ledger sequence safety uses account row version updates plus unique `(cashAccountId, ledgerSequence)`, unique `transactionId` constraints, and serializable retry for write conflicts.
7. Ledger balances are derived from latest ledger rows; ledger rows are append-only and are not physically deleted by application code.
8. Validated Jimpitan collections post through `JimpitanFinanceHooks`, create an income transaction with a Jimpitan category, enforce paid-item totals for `PER_HOUSE`, use collection totals for `BULK_TOTAL`, prevent duplicate `sourceCollectionId` posting, and reject mismatched replay keys.

## Expense Approval Flow
1. Approval endpoints use `AuthenticationGuard`, `TenantGuard`, and `PermissionGuard`; repository calls are always scoped by `actor.rtId`.
2. Policy is stored in tenant settings under `expense_approval_policy` and supports threshold amount, auto-approval below threshold, self-approval prevention, approver roles, required approval count, and expiry metadata.
3. Validated expense transactions above threshold require approval request rows assigned to active same-tenant approver memberships with configured roles.
4. Approval decisions are assigned-member only, cannot be repeated after finalization, enforce self-approval policy, and reject the transaction atomically when an approval is rejected.
5. Finance posting independently checks approval state before ledger writes, so direct posting cannot bypass pending, missing, or rejected expense approvals.
6. Approval notification integration writes in-app notification/outbox rows through the Notifications module; Telegram approval commands call the same approval service boundary, while email provider delivery remains excluded.

## Notification Flow
1. Notification endpoints use `AuthenticationGuard`, `TenantGuard`, and `PermissionGuard`; repository calls are always scoped by `actor.rtId`.
2. Creation validates one target per recipient, active same-tenant users/memberships/residents, verified Telegram bindings for Telegram channels, and non-archived recipient state.
3. One notification row is created for each recipient/channel pair; each row gets a matching `NOTIFICATION_DELIVERY_REQUESTED` outbox event and audit log inside the same database transaction.
4. `idempotencyKey` and `dedupeKey` replay existing notifications only when the request fingerprint matches, preventing duplicate or mismatched outbox fanout.
5. Current-user inbox reads default to `IN_APP`, use `readAt` for read state, and expose unread counts plus mark-one/mark-all read mutations.
6. Admin delivery endpoints list status, cancel pending/failed rows, retry failed rows by creating one new outbox event, safely replay already-pending retries, and block unsafe final-state transitions.
7. Telegram delivery is implemented by the Telegram module outbox adapter; email delivery remains a no-op hook foundation.

## Telegram Bot Flow
1. `POST /api/v1/telegram/webhook` is public, verifies the configured Telegram secret header with constant-time comparison, redacts bind codes from stored payloads, upserts the Telegram account, and stores each incoming update by unique `telegramUpdateId`.
2. Duplicate updates are skipped before command routing to prevent replayed collection input, finance drafts, approval decisions, or notification sends.
3. `/bind <code>` verifies a hashed one-time bind code stored in tenant settings, creates a verified `TelegramBinding`, and audits the binding.
4. Bound accounts resolve active same-tenant membership context into `AuthPrincipal`; multi-RT users select context with `/menu <rtCode>` or a stored tenant session.
5. Bot commands and in-progress state transitions enforce the same permission keys as REST routes before calling Jimpitan, Finance, Cash Account, Category, and Approval services.
6. Stateful flows store minimal tenant-scoped session data in `Setting` rows keyed by Telegram account.
7. Telegram notification delivery claims pending outbox rows conditionally after tenant, aggregate, channel, account, status, and active binding checks, sends via the sender port, and records `SENT` or `FAILED` with audit logs.

## Reporting Flow
1. Private report endpoints use `AuthenticationGuard`, `TenantGuard`, and `PermissionGuard`; repository calls are scoped by `actor.rtId`.
2. Finance, cash-flow, expense category, and public finance reports derive from immutable `cash_ledgers` joined to same-tenant `POSTED` transactions only; finance summary balances use the latest ledger row at or before `dateTo`.
3. Collection reports read tenant-scoped collections, items, houses, and areas; performance defaults exclude draft/rejected/cancelled collections, aggregate `BULK_TOTAL` from collection totals, and outstanding reports exclude inactive/deleted houses, inactive/deleted areas, and total-only sessions.
4. Public serializers never expose resident personal data, internal notes, audit rows, approval internals, or ledger row detail.
5. Public endpoints resolve active, non-deleted RT codes and return public-safe cash balance totals, monthly totals, public metadata, and published announcements.
6. Export requests validate filter JSON safety, write tenant-scoped `report_exports` rows, replay matching idempotency keys, reject mismatched replays, move CSV exports through `PENDING`/`PROCESSING`/`COMPLETED`/`FAILED`/`EXPIRED`, neutralize CSV formula-like cells, audit export mutations/downloads, and expose public-safe CSV routes.

## Worker Flow
1. `src/worker/main.ts` starts a NestJS application context and registers SIGTERM/SIGINT handlers for graceful shutdown.
2. `WorkerService` reads `WORKER_QUEUES`, `WORKER_BATCH_SIZE`, `WORKER_POLL_INTERVAL_MS`, `WORKER_STALE_JOB_MS`, and `WORKER_HEALTH_FILE` from validated config.
3. `report-exports` recovers stale `PROCESSING` CSV exports, then claims queued CSV report exports through `ReportsService.processPendingCsvExports`, which preserves requested-user audit context.
4. `notification-outbox` and `telegram-delivery` recover stale Telegram outbox rows and drain Telegram notification outbox rows through `TelegramService.processTelegramOutbox` once per worker pass.
5. The worker wakes promptly on stop requests and writes a heartbeat file for container health checks after each successful processing pass.
