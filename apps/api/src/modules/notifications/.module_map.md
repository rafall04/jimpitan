# Notifications Module Map

## Scope
- Tenant-scoped in-app notification creation, inbox listing, unread count, mark-read, mark-all-read, delivery administration, retry, cancellation, idempotency replay validation, outbox writes, and audit logging are implemented.
- Telegram delivery is implemented by the Telegram module outbox adapter; email remains a hook/interface foundation without provider integration.
- Notification creation validates active same-tenant users, memberships, residents, and verified Telegram bindings before writes.

## Files
- `notifications.module.ts`: module wiring for Auth/RBAC guards, controller, service, Prisma repository, and no-op delivery hook bindings.
- `notifications.tokens.ts`: repository and delivery hook DI tokens.
- `domain/notification.types.ts`: notification type names, recipient input shape, record shapes, and mark-all-read result.
- `application/notifications.commands.ts`: command/query contracts and request metadata.
- `application/notifications.service.ts`: application validation and tenant-scoped workflow orchestration.
- `infrastructure/notifications.repository.port.ts`: persistence port for notification workflows.
- `infrastructure/prisma-notifications.repository.ts`: Prisma adapter for recipient validation, notification/outbox writes, delivery lifecycle, retry replay safety, reads, idempotency mismatch protection, and audit logs.
- `infrastructure/notification-delivery.port.ts`: Telegram and email delivery hook interfaces.
- `infrastructure/noop-notification-delivery.ts`: no-op fallback delivery hook implementations; Telegram outbox delivery is handled by `src/modules/telegram`.
- `presentation/notifications.controller.ts`: REST endpoints and RBAC metadata.
- `presentation/dto/notification.dto.ts`: request/query DTO validation and Swagger metadata.

## Flow
1. Protected routes use `AuthenticationGuard`, `TenantGuard`, and `PermissionGuard`.
2. Creation requests use `actor.rtId`, validate one target per recipient, resolve active same-tenant recipients, then create one notification row per recipient/channel pair.
3. Notification creation writes a `NOTIFICATION_DELIVERY_REQUESTED` outbox event and `NOTIFICATION_CREATED` audit log in the same database transaction.
4. Idempotency and dedupe keys replay existing notifications only when the request fingerprint matches; mismatch attempts are rejected and audited.
5. Inbox reads are current-user scoped and default to `IN_APP` notifications.
6. Read-state uses `readAt`; delivery status remains `PENDING`, `SENT`, `FAILED`, or `CANCELLED`.
7. Admin delivery endpoints list status, cancel pending/failed notifications, retry failed deliveries, safely replay already-pending retries, and block unsafe final-state transitions.
8. Approval, jimpitan, and finance modules call `NotificationsService` through hook adapters, keeping provider delivery decoupled; Telegram outbox delivery is drained by the Telegram module, while email remains no-op.
