# Content Module Map

## Scope
- Implements the "blog/kegiatan" content layer on top of the `announcements` table (reused, with a `type` discriminator: ANNOUNCEMENT, ACTIVITY, ARTICLE, GALLERY).
- Owns tenant-scoped authoring CRUD, DRAFT→PUBLISHED→ARCHIVED lifecycle, SEO slugs, cover/gallery image management (delegated to AttachmentsModule), content audit logs, and the public content feed/detail/reaction endpoints.
- Public reads are PUBLISHED + PUBLIC only and resolved by RT `code`. Reactions are anonymous, deduped per visitor fingerprint, and mirror a `reaction_count` onto the post.
- Does not implement file storage itself (see AttachmentsModule), notifications, or the legacy `reports/public/:rtCode/announcements` feed (kept for backward compatibility).

## Files
- `content.module.ts`: imports AuthModule, RbacModule, AttachmentsModule; wires controllers, service, repository binding.
- `content.tokens.ts`: `CONTENT_REPOSITORY` provider token.
- `domain/content.types.ts`: authoring records, list rows, and public-safe content shapes.
- `domain/slug.util.ts`: pure slugify + tenant-unique slug resolver.
- `domain/content.policy.ts`: content-type ⇄ Indonesian URL-path mapping and publish-state rules.
- `application/content.commands.ts`: create/update/list/reaction command contracts + request metadata.
- `application/content.service.ts`: slug generation, lifecycle, event-date validation, cover/gallery rules, public lookups.
- `infrastructure/content.repository.port.ts`: persistence port (authoring + public + reactions).
- `infrastructure/prisma-content.repository.ts`: Prisma implementation with in-transaction audit, slug checks, public reads (+view count), and deduped reactions with a count mirror.
- `presentation/content.controller.ts`: `/api/v1/content` authoring routes + RBAC (`content.*`) + multipart image uploads.
- `presentation/public-content.controller.ts`: `/api/v1/content/public/:rtCode/...` feed, detail-by-type+slug, and reaction routes (`@PublicRoute`).
- `presentation/dto`: request/query validation and OpenAPI metadata.

## Flow
1. Authoring controller resolves `CurrentUser`, validates DTOs, and passes correlation metadata; routes require `content.*` permissions.
2. Service uses only `actor.rtId` for tenant scope, generates a tenant-unique slug on create, resolves status from the `publish` flag, and validates event date ranges.
3. Repository applies `rtId` + soft-delete filters to reads and writes audit logs in the same transaction as mutations.
4. Cover/gallery uploads delegate to `AttachmentsService` (owner type ANNOUNCEMENT, owner id = post id); a post has at most one cover.
5. Public controller routes are `@PublicRoute()`; the repository resolves the RT by `code` (case-insensitive) and returns PUBLISHED + PUBLIC posts only.
6. Reactions upsert one row per `(announcement, visitorHash)` then recompute the `reaction_count` mirror inside a transaction.
