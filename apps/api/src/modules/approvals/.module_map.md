# Approvals Module Map

## Scope
- Implements expense approval policy, threshold evaluation, approval request lifecycle, approval decision processing, approval queues, audit logs, RBAC metadata, tenant isolation, and notification hook interfaces.
- Reports, public dashboards, analytics, and payment gateway logic are not implemented; Telegram approval actions call this module through `ApprovalsService`.

## Files
- `approvals.module.ts`: module imports, controller/service registration, Prisma repository binding, and notification hook binding.
- `approvals.tokens.ts`: repository and hook provider tokens.
- `domain/approval.types.ts`: approval policy, approval record, transaction summary, and derived approval state types.
- `application/approvals.commands.ts`: approval query, request, decision, cancellation, policy, and request metadata contracts.
- `application/approvals.service.ts`: policy evaluation, lifecycle validation, self-approval checks, hook dispatch, and tenant-scoped not-found handling.
- `infrastructure/approvals.repository.port.ts`: persistence port for policy, queue, approval request, decision, and cancellation workflows.
- `infrastructure/approval-notification.hooks.port.ts`: decoupled notification event contract.
- `infrastructure/noop-approval-notification.hooks.ts`: no-op notification hook implementation.
- `infrastructure/prisma-approvals.repository.ts`: Prisma implementation for approval policies, immutable approval history, atomic decisions, and audit logs.
- `presentation/approvals.controller.ts`: `/api/v1/approvals` REST routes with RBAC metadata.
- `presentation/dto/approval.dto.ts`: class-validator and Swagger DTOs for approval APIs.

## Flow
1. Controllers enforce Auth, Tenant, and Permission guards, then pass `CurrentUser` and request metadata.
2. Services evaluate tenant policy, validate expense transaction state, prevent self-approval, and dispatch notification hooks; Telegram decisions reuse this service boundary.
3. Repository requests approval rows for active same-tenant approver memberships and keeps approval rows append-style through status transitions.
4. Approval decisions update the approval row and transaction rejection atomically inside one serializable transaction.
5. Finance posting independently rechecks approval state before ledger posting, so direct posting cannot bypass pending or rejected approvals.
