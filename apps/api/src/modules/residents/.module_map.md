# Residents Module Map

## Scope
- Implements tenant-scoped resident REST endpoints.
- Owns resident CRUD, archive/reactivate lifecycle, house moves, optional Telegram account binding, RBAC decorators, Prisma persistence, house occupancy synchronization, and resident audit logs.
- Does not implement jimpitan collection, finance posting, reporting, Telegram bot commands, import/export, or public transparency endpoints.

## Files
- `residents.module.ts`: module imports, controller, service, and repository DI binding.
- `residents.tokens.ts`: repository provider token.
- `domain/residents.types.ts`: safe resident, house summary, and Telegram validation shapes.
- `application/residents.commands.ts`: resident commands, query contracts, and audit request metadata.
- `application/residents.service.ts`: tenant-scoped resident use cases and lifecycle validation.
- `infrastructure/residents.repository.port.ts`: persistence port.
- `infrastructure/prisma-residents.repository.ts`: Prisma implementation, Telegram binding writes, occupancy sync, and audit writes.
- `presentation/residents.controller.ts`: `/api/v1/residents` routes and RBAC metadata.
- `presentation/dto`: request/query validation and OpenAPI metadata.

## Flow
1. Controller resolves `CurrentUser`, validates DTOs, and passes correlation metadata.
2. Service uses only `actor.rtId` for tenant scope, validates target houses, and validates Telegram binding safety.
3. Repository applies `rtId` plus active/archive filters to reads, rechecks target house and Telegram binding state inside write transactions, and writes audit logs in the same transaction as mutations.
4. Resident create/reactivate/move marks target house occupied when needed.
5. Resident archive/move marks the previous house empty only when no active residents remain.
6. Resident moves require an active resident; reactivation rejects residents that are already active.
