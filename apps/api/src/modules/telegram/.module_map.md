# Telegram Module Map

## Scope
- Implements Telegram webhook ingestion, update idempotency, account binding, tenant context selection, role-aware menu, command routing, minimal session state, mode-aware Jimpitan input for `PER_HOUSE` and `BULK_TOTAL`, finance quick commands, approval actions, Telegram notification outbox delivery, RBAC, tenant isolation, and audit logging.
- Uses existing `TelegramAccount`, `TelegramBinding`, `TelegramUpdate`, `Setting`, `Notification`, and `OutboxEvent` schema tables.
- Excludes frontend UI, reports engine, payment gateway, public transparency pages, and email provider integration.

## Files
- `telegram.module.ts`: module imports and provider bindings for controller, service, Prisma repository, and Telegram sender adapter.
- `telegram.tokens.ts`: repository and sender DI tokens.
- `domain/telegram.types.ts`: inbound update, bot reply, binding context, session, webhook result, and outbox delivery types.
- `application/telegram.commands.ts`: webhook metadata, binding-code command, and outbox drain contracts.
- `application/telegram-jimpitan-mode.flow.ts`: selector for `PER_HOUSE` and `BULK_TOTAL` bot input states.
- `application/telegram.service.ts`: webhook secret validation, update routing, binding, tenant resolution, RBAC checks, command flows, state machine, stale outbox recovery, and outbox processing.
- `application/telegram.service.spec.ts`: webhook idempotency, secret validation, bind-code redaction, binding scope, tenant selection, RBAC, per-house and bulk-total Jimpitan flows, amount validation, approval idempotency, and outbox failure tests.
- `infrastructure/telegram.repository.port.ts`: persistence boundary for updates, contexts, sessions, binding codes, audit, and outbox status.
- `infrastructure/telegram-sender.port.ts`: Telegram send-message adapter contract.
- `infrastructure/fetch-telegram.sender.ts`: Telegram Bot API `sendMessage` adapter.
- `infrastructure/prisma-telegram.repository.ts`: Prisma adapter for redacted idempotent update storage, binding verification, tenant context resolution, session settings, stale outbox recovery, outbox claiming, status transitions, active binding checks, and audit logs.
- `infrastructure/prisma-telegram.repository.spec.ts`: outbox tenant/status/aggregate and inactive binding delivery safety tests.
- `presentation/telegram.controller.ts`: public webhook plus protected binding-code and outbox drain endpoints.
- `presentation/dto/telegram.dto.ts`: class-validator and Swagger DTOs.

## Flow
1. `POST /api/v1/telegram/webhook` verifies `x-telegram-bot-api-secret-token` with constant-time comparison when configured, parses the update, redacts bind codes from stored payloads, upserts the Telegram account, and writes `TelegramUpdate` by unique `telegramUpdateId`.
2. Duplicate update IDs return without command execution, preventing replay and duplicate bot-side financial effects.
3. `/bind <code>` verifies a hashed one-time code stored in tenant settings, creates or updates a verified `TelegramBinding`, links the Telegram account to the active same-tenant membership, and audits the binding.
4. Commands resolve verified active bindings to current `AuthPrincipal` data; multi-RT users must select context with `/menu <rtCode>` or use the latest tenant session.
5. Every command and in-progress state transition checks the same permission keys used by REST routes before calling Jimpitan, Finance, or Approval services.
6. Session state is stored minimally in tenant `Setting` rows keyed by Telegram account and expires in the service layer.
7. Jimpitan input reads the selected collection mode before state transition. `PER_HOUSE` selects house, amount/status, and note before saving one item through `JimpitanService`; `BULK_TOTAL` asks only for total amount and optional note before calling `setBulkCollectionTotal`.
8. Finance commands create income/expense drafts through `FinanceTransactionsService` using the default cash account and active categories.
9. Approval actions call `ApprovalsService` and treat already-finalized decisions as idempotent bot responses.
10. Outbox delivery returns stale `PROCESSING` Telegram notification events to `PENDING`, claims pending events only when aggregate, tenant, channel, account, and notification status match; sends through the sender port; catches provider exceptions; then conditionally records `SENT` or `FAILED`.
